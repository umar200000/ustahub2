Tezkor xizmat (Express) — to'liq, batafsil tushuntirish
Mijoz "shu yerga, hoziroq" usta chaqiradigan rejim. Tizim eng yaqin ustalarni avtomatik, birma-bir 60 soniyadan chaqiradi; kim birinchi
rozi bo'lsa, buyurtma darhol yaratiladi.
1. Bu nima va nima uchun kerak?
Oddiy buyurtma: mijoz xizmatni tanlaydi → ustaga so'rov yuboradi → usta qabul qiladi → to'lov → bajariladi. Bu rejalashtirilgan ish uchun.
Tezkor xizmat — "shu yerga, hoziroq usta kerak" holati uchun (avtoelektrik yo'lda qoldi, suv quvuri yorildi, sartarosh uyga kerak). Mijoz bitta
ustani tanlab o'tirmaydi — tizim eng yaqin ustalarni avtomatik, birma-bir 60 soniyadan chaqiradi, kim birinchi rozi bo'lsa, buyurtma
darhol yaratiladi. Bu Yandex Taxi'ning haydovchi qidirish mantig'iga o'xshaydi.
Asosiy farqlar oddiy buyurtmadan:
Mijoz ustani tanlamaydi — tizim masofa bo'yicha tanlaydi.
Buyurtma to'g'ridan-to'g'ri ACTIVE holatda yaratiladi (payment/pending bosqichi yo'q).
Real-time: WebSocket + push xabar.
2. Ishtirokchilar
Kim Roli
Mijoz (client) Qidiruvni boshlaydi, natijani kutadi
Usta (master) So'rovni oladi, 60s ichida qabul/rad qiladi
Tizim Navbat tuzadi, ustalarni birma-bir chaqiradi, timeout boshqaradi, buyurtma yaratadi
3. To'liq oqim — jonli misol bilan
Ssenariy: Dilnoza Toshkentda, Chilonzorda. Mashinasi yurmay qoldi — avtoelektrik kerak, hoziroq.

Bu narxlarni ( base_price , max_price ), reytingni ko'rsatadi. Dilnoza aniq bitta xizmatni tanlashi yoki o'tkazib yuborishi mumkin (u holda
butun kategoriya bo'yicha qidiriladi).
Qadam 3 — Qidiruvni boshlaydi
POST /api/v1/client/express/search/
{
"category_id": "a0629ad5-...-abbac",
"province_id": "ea57c322-...-e4e6",
"district_id": "b2c87561-...-63e8",
"latitude": 41.311081,
"longitude": 69.279716,
"payment_method": "cash"

Tizim shu zahoti nima qiladi (eng muhim qism):
1. Tekshiruv: Dilnozada allaqachon faol qidiruv bormi? Bo'lsa → 400 ("Avval uni bekor qiling"). Bir vaqtda faqat bitta faol qidiruv.
2. Navbat tuzish (PostGIS bilan) — quyidagi shartlarga mos ustalar topiladi: - shu kategoriyada aktiv tezkor xizmati bor, - is_active
= true (faol) va is_available = true (bo'sh), - shu viloyatda ( province_id mos), - lokatsiyasi bor ( home_location ), -
(tuman berilgan bo'lsa) shu tumanda.
Topilgan ustalar mijozdan masofa bo'yicha saralanadi (PostGIS ST_Distance , kilometrda). Natija: navbat = [ {master: Akmal, 2.4
km}, <- eng yaqin, birinchi chaqiriladi {master: Bobur, 3.1 km}, {master: Sardor, 5.8 km}, ... ]
3. Sessiya yaratiladi ( express_search_sessions jadvali): status=searching , navbat, lokatsiya, payment_method saqlanadi.
4. Birinchi ustaga (Akmal) xabar yuboriladi — push + WebSocket. notified_at = hozir , current_master_id = Akmal .
5. 60 soniyalik soat ishga tushadi (Celery express_master_timeout , countdown=60 ).
Javob (Dilnozaga):

"session_id": "7c9e6679-...-90ae7",
"status": "searching",

5. Ichki mexanizmlar — chuqurroq
a) Navbat va masofa
Masofa PostGIS orqali aniq geografik hisoblanadi ( ST_Distance , metrda → km). Navbat bir marta, qidiruv boshida tuziladi va saqlanadi
( master_queue JSONB). Har chaqirilgan usta tried_master_ids ga ko'chadi.
b) Timeout va Celery
Har bir ustaga 60s. Buni Celery boshqaradi ( express_master_timeout , countdown=60 ). Bu alohida jarayonda ishlagani uchun, hatto API
restart bo'lsa ham timeout ishlaydi.
c) Race condition himoyasi (juda muhim)
Usta aynan 60-soniyada "accept" bosishi va timeout task ayni damda ishlashi mumkin. Ikkalasi ham sessiyani SELECT FOR UPDATE bilan
bloklab oladi — shuning uchun bir vaqtda ikkita usta bitta so'rovni qabul qila olmaydi yoki buyurtma ikki marta yaratilmaydi. Timeout task
qo'shimcha notified_at < 55s tekshiruvi bilan erta ishlab ketishdan himoyalanadi.
d) Real-time: nega WebSocket + FCM ikkalasi?
WebSocket — ilova ochiq bo'lganda darhol yetkazadi.
FCM push — ilova fonda/yopiq bo'lganda zaxira yo'l.
Redis pub/sub — API bir nechta worker'da, Celery alohida jarayonda. WS ulanish faqat bitta worker xotirasida yashaydi; boshqa
joyda yuzaga kelgan hodisa Redis kanali orqali to'g'ri worker'ga uzatiladi. Yetkazib bo'lmasa ham buyurtma oqimi buzilmaydi
(hammasi try/except da).
6. Token va pul — chalkashmang!
Bu ikki alohida narsa:
Token (komissiya) To'lov ( payment_method )
Kim to'laydi Usta / provayder Mijoz
Qachon Usta qabul qilganda darhol yechiladi Hozircha keyin / qo'lda
Nima uchun Platformaning komissiyasi Xizmat narxi
Manba Usta/provayder token balansi Naqd yoki karta
Token: usta accept qilganda balansidan komissiya token yechiladi (solo usta uchun token_cost_solo_master , provayder ustasi
uchun token_cost_provider — platforma sozlamalaridan). Yetmasa buyurtma yaratilmaydi.
To'lov: cash yoki card . Buyurtmaga yorliq qo'yiladi, lekin hozir avtomatik pul yechilmaydi ( is_paid=false ). card +
EXPRESS_CARD_AUTOCHARGE=true bo'lsagina kartadan avtomatik yechiladi — lekin bu flag productionda false , shuning uchun
hozir karta ham faqat yorliq.

4. Usta kanali — to'liq servis (reconnect bilan)
Usta ilovasi ochiq turganda doimiy ulanib turadi va express_request keladi.
import 'dart:async';
import 'dart:convert';
import 'package:web_socket_channel/web_socket_channel.dart';
import 'package:web_socket_channel/status.dart' as ws_status;
class ExpressMasterSocket {
ExpressMasterSocket({required this.accessToken});
static const _base = 'ws://3.64.241.75:8000/api/v1/ws/express';
final String accessToken;
WebSocketChannel? _channel;
StreamSubscription? _sub;
Timer? _reconnectTimer;
int _retry = 0;
bool _closedByUser = false;
final _events = StreamController<Map<String, dynamic>/.broadcast();
Stream<Map<String, dynamic>/ get events => _events.stream;
Future<void> connect() async {
_closedByUser = false;
final uri = Uri.parse('$_base/master?token=$accessToken'); // SLASHSIZ!
final channel = WebSocketChannel.connect(uri);
_channel = channel;
try {
await channel.ready; // 403 (token) yoki tarmoq xatosi shu yerda otiladi
_retry = 0;
} catch (_) {
_scheduleReconnect(); // token yangilash kerak bo'lishi mumkin
return;
}
_sub = channel.stream.listen(
(data) {
try {
_events.add(jsonDecode(data as String) as Map<String, dynamic>);
} catch (_) {// notext frame'larni e'tiborsiz qoldir */}
},
onDone: _scheduleReconnect,
onError: (_) => _scheduleReconnect(),
cancelOnError: true,
);
}
void _scheduleReconnect() {
if (_closedByUser) return;
_sub?/cancel();
final secs = (1 </ _retry).clamp(1, 30); // 1,2,4,8,16,30s backoff
_retry = (_retry + 1).clamp(0, 5);
_reconnectTimer?/cancel();
_reconnectTimer = Timer(Duration(seconds: secs), connect);
}
void dispose() {
_closedByUser = true;
_reconnectTimer?/cancel();
_sub?/cancel();
_channel?/sink.close(ws_status.normalClosure);
_events.close();
}
}

=== express-websocket-topshiriq.pdf ===
Express WebSocket — Flutterchiga topshiriq
Push (Firebase) allaqachon ishlayapti. Endi faqat WebSocket qo'shiladi — u push'ning real-time juftligi: ilova ochiq bo'lganda WS
orqali darhol keladi, ilova fonda/yopiq bo'lganda eski push orqali keladi.
Eng muhim yaxshilik: WS xabarlari push data bilan aynan bir xil formatда ( type maydoni bilan). Shuning uchun mavjud push
handleringni qayta ishlatasan — WS'dan kelgan JSON'ni o'sha switch(type) ga uzatsang bo'ldi.
1. Kutubxona
web_socket_channel: ^3.0.0
2. Ulanish manzillari
Token = login'dan olingan o'sha access_token (REST'dagi Bearer bilan bir xil), faqat URL query'da uzatiladi (header emas):
Usta (24/7 ulanib turadi):
ws://3.64.241.75:8000/api/v1/ws/express/master?token=<access_token>
Mijoz (qidiruv davomida):
ws://3.64.241.75:8000/api/v1/ws/express/client/{session_id}?token=<access_token>
⚠ URL oxirida / (slash) YO'Q — bo'lsa 403 qaytadi. (REST'da aksincha — slash bor.)
3. Token
WS uchun token = REST'dagi Bearer token bilan bir xil, faqat ?token= qilib uzatiladi.
Token muddati tugasa WS handshake 403 beradi → refresh qilib qayta ulanasan ( channel.ready da ushlanadi).
⚠
4. Cleartext ruxsati — SHART (faqat WS uchun yangi)
ws:// (TLS'siz) ulanish Android 9+ va iOS'da default bloklangan. Push'ga bu kerak emas edi, WS'ning yagona qo'shimcha sozlamasi shu.
Bo'lmasa release build'da ulanmaydi.
Android — android/app/src/main/res/xml/network_security_config.xml :
<?xml version="1.0" encoding="utf-8"?>
<network-security-config>
<domain-config cleartextTrafficPermitted="true">
<domain includeSubdomains="false">3.64.241.75</domain>
</domain-config>
</network-security-config>
AndroidManifest.xml → <application android:networkSecurityConfig="@xml/network_security_config" .//>
iOS — ios/Runner/Info.plist :
<key>NSAppTransportSecurity</key>
<dict>
<key>NSExceptionDomains</key>
<dict>
<key>3.64.241.75</key>
<dict>
<key>NSExceptionAllowsInsecureHTTPLoads</key><true//
<key>NSIncludesSubdomains</key><false//
</dict>
</dict>
</dict>
5. Keladigan xabarlar — push bilan BIR XIL
Usta kanali: express_request (yangi tezkor so'rov)
Mijoz kanali: express_matched (usta topildi), express_no_masters (topilmadi)
Ulanishda: {"type":"status","status":"connected"}
WS'dan kelgan matnni jsonDecode qilib, mavjud push handleringдаги switch(msg['type']) ga yubor.
Eslatma: express_request da distance_km , client_latitude , client_longitude — string bo'lib keladi (push'dagi kabi) →
double.parse(.//) .
6. Javob qaytarish — REST (o'zgarmagan)
POST /api/v1/master/express/respond/
{ "session_id": ".//", "action": "accept" } // yoki "reject"
7. Ulanish hayotiy davri
Usta: login'dan keyin WS ochiladi va doimiy ochiq turadi (uzilsa avto-reconnect — backoff bilan).
Mijoz: POST /client/express/search/ chaqirib session_id olgach WS ochadi, natijani kutadi, natija kelgach yopadi. (WS
ishlamasa zaxira: GET /client/express/search/{id}/status/ polling.)
